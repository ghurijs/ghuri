# Migrations

Generating, writing, applying and rolling back migrations (`@ghuri/orm/migrations`, `ghuri makemigrations` / `migrate`), on D1, SQLite and Postgres.

## The loop

```sh
npx ghuri makemigrations            # all apps; or: npx ghuri makemigrations blog
npx ghuri migrate                   # local D1 (Miniflare state in .wrangler/state), or DATABASES.default
npx ghuri showmigrations            # [X] applied / [ ] pending
npx ghuri sqlmigrate blog 0002      # print the SQL (--dialect sqlite|postgresql, --backwards)
npx ghuri migrate --remote          # production D1 (needs wrangler login + real database_id)
npx ghuri migrate --database pg     # another DATABASES alias
```

Run `makemigrations` after every model change and commit the generated files together with the model change. Never hand-write `CREATE TABLE` SQL or use `drizzle-kit` / `wrangler d1 migrations create` for Ghuri models.

## How an app is wired for migrations

Workers have no filesystem, so migrations are imported, not discovered:

```ts
// src/blog/app.ts
import { AppConfig } from '@ghuri/core'
import * as admin from './admin'
import * as migrations from './migrations'
import * as models from './models'

export class BlogConfig extends AppConfig {
  name = 'blog'
  path = import.meta.dirname   // CLI only: where migrations/ is written
  models = models
  migrations = migrations      // the generated migrations/index.ts
  admin = admin
}
```

```
src/blog/migrations/
├── 0001_initial.ts
├── 0002_post_summary.ts
└── index.ts            # regenerated by makemigrations on every run; do not edit
```

`ghuri startapp` creates `migrations/index.ts` for you. An app without `path` is skipped by `makemigrations`.

## A migration file

Fields are plain data (`{ type, ...options }`) and never import your models:

```ts
// src/blog/migrations/0002_post_summary.ts
import { Migration, operations as ops } from '@ghuri/orm/migrations'

export default new Migration({
  dependencies: [['blog', '0001_initial']],
  operations: [
    ops.AddField({
      modelName: 'Post',
      name: 'summary',
      field: { type: 'CharField', maxLength: 300, blank: true, default: '' },
    }),
    ops.AddField({
      modelName: 'Post',
      name: 'code',
      field: { type: 'SlugField' },
      oneOffDefault: 'post',   // fills existing rows only; not kept on the field
    }),
  ],
})
```

`Migration` options: `dependencies`, `operations`, `initial`, `replaces`, `atomic` (default true), `runBefore`. Generated names follow Django (`0001_initial`, `0002_post_slug`, `0003_remove_post_body`); `--name` overrides the suffix.

## Operations (`ops.X(...)`)

| Operation | Purpose |
|---|---|
| `CreateModel`, `DeleteModel`, `RenameModel` | tables |
| `AlterModelTable`, `AlterModelOptions`, `AlterUniqueTogether` | table name, Meta options |
| `AddField`, `RemoveField`, `AlterField`, `RenameField` | columns |
| `AddIndex`, `RemoveIndex`, `AddConstraint`, `RemoveConstraint` | indexes and constraints |
| `RunSQL({ sql?, sqlite?, postgresql?, reverse?, stateOperations? })` | raw SQL, per dialect (a dialect without SQL is skipped) |
| `RunCode(forwards, backwards?)` | data migration in TypeScript (Django's `RunPython`) |

`ops.RunSQL.noop` and `ops.RunCode.noop` are reversible no-ops.

```ts
import { operations as ops } from '@ghuri/orm/migrations'

const backfill = ops.RunSQL({
  sqlite: "UPDATE blog_post SET slug = lower(title) WHERE slug = ''",
  postgresql: "UPDATE blog_post SET slug = lower(title) WHERE slug = ''",
  reverse: ops.RunSQL.noop,
})
```

## Data migrations

```sh
npx ghuri makemigrations blog --empty --name backfill_summaries
```

```ts
// src/blog/migrations/0003_backfill_summaries.ts
import { Migration, operations as ops } from '@ghuri/orm/migrations'

export default new Migration({
  dependencies: [['blog', '0002_post_summary']],
  operations: [
    ops.RunCode(
      async (apps, conn, { using }) => {
        const Post = apps.getModel('blog', 'Post')   // historical model, NOT your current class
        for await (const post of Post.objects.using(using).filter({ summary: '' })) {
          post.summary = String(post.body).slice(0, 280)
          await post.save({ updateFields: ['summary'], using })
        }
      },
      ops.RunCode.noop,
    ),
  ],
})
```

- Always `apps.getModel()` inside `RunCode`; never import models from `../models` (they may have fields the DB doesn't have yet; custom methods aren't available on historical models).
- The second argument is the `Connection` (`await conn.execute(...)`), the third carries `using`; pass `using` to queries so `--database` works.
- On D1, statements before a `RunCode` are sent as their own batch and the callback's writes apply as they happen: keep data migrations idempotent.

## What makemigrations detects and asks

- Created/deleted/renamed models and fields, altered fields, M2M fields, `Meta.indexes`, `constraints`, `uniqueTogether`, `dbTable`, other Meta options, cross-app dependencies (FK cycles split into two migrations).
- Interactive by default: asks "did you rename?" and for a one-off default when adding a NOT NULL field without a default. In agents/CI (no TTY) use `--no-input`: renames become remove + add (data loss!) and a NOT NULL field without default is an error. So for non-interactive runs give new fields a `default`, `null: true`, or edit the generated file to use `ops.RenameField` / `ops.RenameModel`.
- Not detected / not supported: changing a model's primary key or auto-field type, swappable-dependency markers. `squashmigrations` and `inspectdb` do not exist.

## Flags

| Command | Options |
|---|---|
| `makemigrations [app...]` | `-n/--name`, `--empty`, `--dry-run`, `--check` (CI: non-zero if missing), `--merge`, `--no-input` |
| `migrate [app] [name]` | `--fake`, `--fake-initial`, `--plan`, `--run-syncdb`, `--no-input`, `--database <alias>` |
| `showmigrations [app...]` | `-p/--plan`, `--database` |
| `sqlmigrate <app> <name>` | `--backwards`, `--dialect`, `--database`; `--all --out <dir>` for wrangler |

Rollback: `npx ghuri migrate blog 0002` (unapply later ones), `npx ghuri migrate blog zero`. `RunSQL` without `reverse` / `RunCode` without backwards raise `IrreversibleError` when rolled back. Branch conflicts: `npx ghuri makemigrations --merge`.

## Dialects and D1

- Same migration files run on D1, SQLite and Postgres (that is what makes D1 -> Postgres a settings change).
- SQLite/D1: column changes that SQLite can't `ALTER` rebuild the table (copy through a temp table with `PRAGMA defer_foreign_keys = ON`); data is kept. Check big tables first with `sqlmigrate --dialect sqlite`.
- D1: each migration plus its `ghuri_migrations` row is sent as one atomic batch. Postgres/SQLite: one transaction per migration.
- Applied migrations are recorded in `ghuri_migrations` (not `django_migrations`).
- Letting wrangler apply SQL instead: `npx ghuri sqlmigrate --all --out migrations-sql`, set `migrations_dir` in `wrangler.jsonc`, then `npx wrangler d1 migrations apply DB --remote`. Pick one method per database.

## Programmatic API (Workers-safe)

```ts
import { migrate, showMigrations, sqlMigrate } from '@ghuri/orm/migrations'

await migrate({ using: 'default' })
await migrate({ appLabel: 'blog', target: 'zero' })
const statements = await sqlMigrate('blog', '0002', { dialect: 'postgresql' })
const status = await showMigrations()   // [{ app, name, applied, dependencies }]
```

Signals: `preMigrate` / `postMigrate` from `@ghuri/orm` fire per app (`{ appConfig, using, plan }`); `@ghuri/auth` uses `postMigrate` to create content types and permissions.

## Gotchas

- `python manage.py makemigrations` / `RunPython(forwards)` / sync functions: use `npx ghuri makemigrations` and `ops.RunCode(async (apps, conn, { using }) => {...})`.
- Editing `migrations/index.ts` by hand, or forgetting `migrations = migrations` / `path = import.meta.dirname` on the AppConfig (then nothing is generated or applied on Workers).
- Importing app models inside a migration: use `apps.getModel('blog', 'Post')`.
- Using `drizzle-kit`, Prisma migrate, or hand-written `wrangler d1` SQL for Ghuri models.
- Running `migrate` locally and assuming production is updated: production D1 needs `--remote` (or `ghuri deploy --migrate`); Postgres needs `--database <alias>` or the right `DATABASE_URL`.
- Changing `AUTH_USER_MODEL` after the first migration.
- Editing a migration already applied elsewhere: write a new one.
